# 售后正常流程的缓存校验失败定位

此改动只补充正常隔离执行的失败定位，不修复缓存内容，也不代表售后流程已经通过验收。

`ms4-aftersale-review-normal.php` 保持原来的 40 项顺序、缓存 GET、空值跳过、类型和期限校验，以及 `TASK78_WARM_EXACT_SERIALIZED_SOURCE_VALUE` 的原布尔条件和异常。

只有该断言真实失败时，程序才尽力保存以下元数据，并重新抛出同一个原始异常：

| 字段 | 含义 |
| --- | --- |
| ordinal | 原 40 项中的序号，包含前面跳过的空值项 |
| logical_name | 与该序号严格对应的固定配置或语言缓存名称 |
| expected_null | 数据库来源的逻辑值是否为 null |
| expected_wire_bytes / expected_wire_sha256 | 原序列化规则生成的期望字节长度及 SHA-256 |
| raw_type | 本次已有 GET 返回值的 PHP 类型，不是 Redis TYPE |
| raw_bytes / raw_sha256 | 仅字符串返回值的长度及 SHA-256；其它类型均为空 |

失败结果仅在原阶段、原错误码、同一异常四项指纹和严格八字段资格都吻合时，增加可选的 `warm_failure_context`。正常成功结果保持原 29 个顶层字段；原 `diagnostic`、外层异常处理和 shutdown 记录保持。

定位记录不包含缓存值、序列化正文、凭据或异常堆栈。元数据构造失败不会替换原始失败，也不会触发额外缓存读取、补写、清理或业务重试。`expected_null` 可以来自缺行、SQL NULL 或 JSON 解码结果，不能据此唯一认定数据缺失。

已完成源码复核和固定候选的 PHP 8.2 纯语法检查。后续仍须按原完整正常链验证；历史失败项和根因尚未确定，不运行故障注入样本，也不放宽原断言。
