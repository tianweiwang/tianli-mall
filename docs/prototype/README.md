# 天俪商城 · 加盟平台交互原型

给甲方演示业务流程用的静态原型。**不是可运行的功能**，与主项目代码完全隔离。

## 打开方式

直接双击 `index.html` 即可，无需构建、无需装依赖。

若浏览器限制本地文件加载 JS，起个静态服务：

```bash
cd docs/prototype
python -m http.server 8099
# 打开 http://127.0.0.1:8099
```

## 演示内容

顶部四个按钮切换角色：

| 角色 | 内容 |
| --- | --- |
| **顾客端** | 扫码进店 → 选时段预约 → 核销码；另有商品详情 → 确认订单 → 支付成功、我的 |
| **门店端** | 工作台（营业额/抽成/待核销）→ 预约管理 → 扫码核销 → 核销成功 |
| **品牌方** | 全平台 GMV、抽成收入、门店排行、门店与分账状态表 |
| **资金流** | 一笔 ¥3,799 订单的完整流向，以及五项前置条件清单 |

宽屏三屏并排展示流程；窄屏（≤640px）自动切为单屏，顶部出现步骤导航。

## 可交互的部分

- 选日期、选时段（满位时段点击会提示）
- 选中时段后「下一步」启用 → 弹出确认层 → 确认后跳转核销码页
- 商品卡片 → 商品详情 → 立即购买 → 微信支付 → 支付成功
- 底部 tabbar、门店端各入口、页面内的跳转按钮

## 页面上的黄色标注

每屏底部的黄色框是**给业务方看的设计说明**，标出该屏对应的技术要点或待定问题，例如：

- 门店归属存在**订单上**而非绑死用户，同一顾客可先后归属不同门店
- 预约名额占位必须用带守卫的单条更新，不能沿用现有商品库存的「先查后写」
- 核销要校验店员 `store_id` 与预约门店一致，防止跨店核销
- 分销佣金由品牌方从抽成中支付，不进微信分账链路
- 退款必须先回退分账再退款，顺序错会失败

演示时可以照着这些标注讲，也可以在正式给甲方看之前删掉（在 `views.js` 里搜 `class="annot"`）。

## 数据来源

- **商品**：取自当前验收库 `eb_store_product` 的真实记录（iPad mini6、护眼台灯等 4 件）
- **门店、预约、分账**：演示数据，系统中尚无这些功能
- **配色**：取自 `template/uni-app` 实际使用的色值（主色 `#e93323`、文字 `#282828`、次要 `#82848f`、背景 `#f5f5f5`）

## 文件结构

```
docs/prototype/
├── index.html          外壳与角色切换
├── README.md           本文件
└── assets/
    ├── app.css         样式（含响应式）
    ├── data.js         演示数据，改这里就能换门店名/商品/金额
    ├── views.js        14 个视图的 HTML
    └── app.js          交互与角色切换
```

想改门店名、商品、抽成比例、时段容量，只改 `data.js` 即可。

## 与实际系统的差距

原型演示的功能中，**目前系统只有商品浏览和下单是真实存在的**。以下都还没有实现：

| 原型中的功能 | 系统现状 |
| --- | --- |
| 门店子商城、扫码归属 | 无门店主体表，`mer_id` 是遗留死字段全为 0 |
| 到店预约 | 完全没有，搜索预约相关代码命中 0 |
| 门店独立收款 | 商户号是全站单一配置，无门店维度 |
| 分账抽成 | 完全没有，搜索 `profitsharing` 命中 0 |
| 门店端后台 | 无 |

完整的能力现状与分期规划见 `docs/superpowers/specs/2026-07-30-tianli-franchise-platform-requirements.md`。
