# 设备数据驱动的体态检测经营平台设计

**用途：** 正式系统业务与技术边界设计，并指导当前加盟平台 H5 Demo 扩展。

**日期：** 2026-07-30

**状态：** 已确认，待书面审阅

**上位设计：** `docs/superpowers/specs/2026-07-30-posture-assessment-system-design.md`

## 1. 背景与目标

甲方向加盟门店提供体态检测设备。设备能够回传结构化检测指标、原始照片或视频，以及设备编号、操作人、检测时间等元数据。设备可通过商城系统生成的一次性检测任务 ID，将检测结果准确关联到会员或门店临时顾客档案。

本设计选择“检测经营闭环”路线，不把系统做成单纯的设备报告库，也不在首期直接建设未经验证的智能健康平台。

正式业务闭环为：

```text
预约或现场建档
  -> 授权确认
  -> 创建检测任务
  -> 设备扫码领取
  -> 检测与数据回传
  -> 系统校验与门店确认
  -> 顾客报告与方案建议
  -> 产品或服务转化
  -> 复评预约
  -> 前后对比与品牌分析
```

目标包括：

- 让设备结果准确、稳定地归属到顾客、门店、设备和操作人。
- 让顾客获得可理解、可追踪的检测档案和复评对比。
- 让门店将检测用于报告解读、方案推荐、成交和复评召回。
- 让品牌方统一管理设备、报告规则、门店质量和效果数据。
- 在合规前提下逐步形成可审计、可研究的数据资产。
- 让当前 H5 Demo 先证明业务闭环，不冒充已经接通真实设备。

## 2. 已确认决策

1. 设备回传结构化指标、原始影像和完整设备元数据。
2. 商城系统创建检测任务 ID，设备扫码领取后按该 ID 回传。
3. 会员优先关联正式用户档案，同时允许门店创建临时顾客档案。
4. 临时档案可在身份验证后合并到正式会员，历史检测记录不得丢失。
5. 采用“检测经营闭环”，暂不直接建设智能预测和自动诊断能力。
6. 先确定正式系统的可落地业务闭环，再将核心流程加入当前 H5 Demo。
7. 原始设备数据不可覆盖；标准化结果、人工复核和报告分别版本化。
8. 门店只能访问本店顾客数据，品牌统计以脱敏汇总为主。

## 3. 范围边界

### 3.1 正式系统包含

- 会员与临时顾客档案。
- 授权、检测任务、设备领取、状态跟踪和结果回传。
- 设备、门店、操作人和校准信息管理。
- 原始载荷与影像归档、指标标准化、完整性校验和人工复核。
- 顾客报告、历史时间线、前后对比和复评预约。
- 品牌方案规则、门店成交跟进和复评召回。
- 设备运营、门店质量、复评与效果分析。
- 访问审计、版本记录和去标识化导出能力。

### 3.2 首期不包含

- 医疗诊断、治疗建议、疗效承诺或自动开具医疗方案。
- 未经验证的 AI 影像测量、效果预测和自动风险诊断。
- 3D 建模、跨品牌设备自动标定和复杂科研统计平台。
- 在未取得明确授权前，将影像或敏感数据用于研究、训练或宣传。
- 仅凭姓名、未验证手机号或设备流水自动合并顾客档案。

## 4. 使用角色

### 4.1 顾客

顾客可能来自线上预约，也可能直接到店。主要目标是快速完成检测、看懂报告、了解变化，并方便安排复评。系统应避免制造恐慌或羞辱性表达，允许顾客查看授权范围和管理自己的档案。

### 4.2 门店顾问或检测操作人

门店人员需要在繁忙环境中快速建档、发起检测、处理设备异常、解释报告和安排后续服务。操作流程必须明确当前顾客和任务，避免错绑；错误提示应说明恢复办法，不能只显示设备错误码。

### 4.3 品牌运营与质量管理人员

品牌方需要管理设备分配、门店使用质量、检测与复评转化，并发现异常数据。品牌人员默认查看汇总和异常线索，只有具备授权的岗位才能因质量复核查看必要明细。

### 4.4 数据与合规人员

负责指标版本、授权范围、审计、数据保留和去标识化导出。研究导出与日常经营访问分离，所有导出必须审批和留痕。

## 5. 系统边界

正式系统划分为五个职责边界。

### 5.1 顾客与授权

- 管理会员、临时顾客和身份合并关系。
- 记录检测、影像、报告、后续运营和研究用途的授权范围。
- 授权未完成时不得让设备领取检测任务。
- 授权撤回后按法律和业务规则限制后续使用，不伪造历史授权状态。

### 5.2 检测任务编排

- 创建一次性、有限期的检测任务。
- 绑定顾客、预约、门店、检测项目、授权记录和允许使用的设备范围。
- 管理设备领取、检测尝试、超时、取消和完成状态。
- 一个任务允许多次检测尝试，但只能确认一份有效结果。

### 5.3 设备接入网关

- 验证设备身份、请求签名、时间戳和防重放字段。
- 接收结构化指标、影像引用、设备流水和运行元数据。
- 处理幂等、分片上传、断网重试、超时和回执。
- 设备端离线缓存必须加密，并在服务端确认完整接收后按约定策略清除。
- 隔离门店、设备或任务不匹配的结果，不直接写入顾客正式档案。

### 5.4 评估档案与报告

- 不可变保存原始设备载荷和原始影像。
- 按版本化指标字典生成标准化指标。
- 保存完整性校验、人工复核和异常标记。
- 生成面向顾客和门店的非医疗报告，并保留报告版本。
- 支持与首次、上次和指定历史检测比较。

“不可变”表示在有效保留期内不能通过普通业务操作覆盖或篡改原始内容；依法执行的整份删除、到期清理和监管处置使用独立流程并完整留痕。

### 5.5 运营与分析

- 管理品牌方案规则、复评周期和召回任务。
- 汇总设备利用率、门店检测质量、成交与复评数据。
- 分析配对样本、依从性和产品方案差异。
- 提供异常线索、审计查询和去标识化研究导出。

## 6. 顾客关联设计

### 6.1 会员顾客

线上预约时直接使用内部用户 ID 创建检测任务。设备不接收用户 ID、手机号或完整姓名，只接收不透明的任务令牌和必要的现场核对信息。

### 6.2 临时顾客

门店可创建临时档案，采集最小必要信息并完成单独授权。临时档案拥有独立内部 ID，可正常承载检测、报告和复评计划。

### 6.3 档案合并

- 顾客完成手机号验证或微信身份确认后才可发起合并。
- 合并前展示两份档案的检测次数、门店和时间，防止误合并。
- 合并保留原临时档案 ID、授权记录和全部审计链路。
- 冲突字段不得静默覆盖，由具备权限的人员选择并记录原因。
- 合并操作可追溯；不以同名、相似手机号或门店人员判断自动执行。

## 7. 设备与任务数据流

### 7.1 创建任务

系统在预约核销前后或现场建档后创建检测任务，保存：

- 检测任务 ID。
- 顾客内部 ID、预约 ID和门店 ID。
- 检测项目与指标字典版本。
- 授权记录 ID及授权范围。
- 允许领取的门店、设备类型和任务有效期。

### 7.2 设备领取

门店端展示任务二维码。设备扫码后向网关领取任务，网关验证设备所属门店、设备状态、校准状态和任务有效期。设备只获得执行检测所需的最小信息。

### 7.3 数据回传

设备至少回传：

- 检测任务 ID与设备检测流水号。
- 检测开始、结束和上传时间。
- 设备编号、型号、软件版本和校准信息。
- 操作人或设备登录人员标识。
- 结构化指标及单位。
- 原始照片、视频或其他原始文件引用。
- 数据协议版本、校验值和回传状态。

### 7.4 校验与确认

网关先保存不可变原始提交，再执行任务匹配、协议版本、字段完整性、单位、合理范围、影像完整性和重复数据校验。通过自动校验的结果进入门店确认；异常结果进入人工复核，不直接生成正式顾客报告。

### 7.5 报告与复评

结果确认后生成版本化报告、时间线节点和复评计划。顾客可查看报告，门店可解读并记录方案建议，品牌方只获得授权范围内的汇总与质量指标。

## 8. 状态模型

正常状态：

```text
待授权
  -> 待设备领取
  -> 检测中
  -> 数据校验中
  -> 待门店确认
  -> 报告已生成
  -> 已完成
```

异常或终止状态包括：任务过期、已取消、检测失败、数据不完整、待人工复核和结果已隔离。

状态规则：

- 授权未完成时设备不得领取任务。
- 任务过期或取消后不得继续生成有效报告。
- 一个任务可包含多个检测尝试，每次尝试保留独立设备流水。
- 同一设备流水和任务 ID重复回传时返回已有处理结果。
- 只有一份检测尝试可被确认成任务有效结果。
- 原始载荷和影像不可修改；复核只能新增版本和说明。
- 报告规则升级时生成新报告版本，旧版本继续可查。

## 9. 异常处理

| 场景 | 处理规则 |
| --- | --- |
| 设备离线 | 设备本地暂存，恢复网络后按原流水重试 |
| 重复回传 | 幂等返回，不生成重复档案 |
| 设备与门店不匹配 | 隔离结果并通知门店和品牌设备管理员 |
| 任务已过期 | 拒绝写入正式档案，门店重新创建任务 |
| 指标或影像缺失 | 标记数据不完整，允许补测或人工复核 |
| 指标超出合理范围 | 保留原始数据，暂停正式报告并要求复核 |
| 检测中断 | 在原任务下新增检测尝试，不覆盖失败尝试 |
| 顾客匹配冲突 | 暂停归档，完成身份验证后人工处理 |
| 门店需要修正 | 新增复核版本，记录原因、操作人和时间 |
| 规则或算法升级 | 生成新标准化结果或报告版本，保留旧版本 |

门店界面必须将设备错误转换成可执行提示，例如“设备网络中断，数据已保存在设备中，请保持本页并等待自动重试”，不能只展示技术错误码。

## 10. 三端功能

### 10.1 消费者端

- 我的检测与任务状态。
- 检测报告、指标解释和原始影像授权展示。
- 与首次、上次或指定记录的前后对比。
- 品牌配置的产品、服务和使用计划建议。
- 从报告进入复评预约。
- 查看授权范围，申请导出或删除档案。

报告不得将顾客贴上负面标签。改善、稳定或波动均以中性语言解释，并明确结果不替代医疗诊断。

### 10.2 门店端

- 检测工作台：待检测、检测中、待确认、失败和待复评。
- 会员检索、临时建档和授权确认。
- 任务二维码、设备领取状态和检测进度。
- 数据完整性确认、补测和人工复核申请。
- 报告解读、方案建议和成交跟进。
- 顾客检测、购买、使用计划、预约和复评时间线。
- 待复评顾客、提醒记录和复评预约。

门店不得修改设备原始数据、品牌指标定义或品牌统一推荐规则。

### 10.3 品牌方后台

- 设备入库、门店分配、在线状态、版本、校准和利用率。
- 检测量、完成率、失败率、平均耗时和门店排行。
- 指标字典、单位、参考范围、解释文案和报告模板版本。
- 产品与服务方案规则、复评周期和门店可见范围。
- 复评率、逾期召回、检测转化和门店质量。
- 配对样本、依从性分层、产品方案与周期效果分析。
- 缺失数据、设备偏差、异常改善和疑似不规范操作预警。
- 数据访问、复核、合并、导出和规则变更审计。

## 11. H5 Demo 扩展

当前 Demo 不连接设备厂商，不新增远程 Mock API。使用确定性的本地设备载荷和状态机模拟：

```text
消费者预约
  -> 门店创建检测任务
  -> 模拟设备扫码领取
  -> 检测中
  -> 固定设备数据回传
  -> 门店确认报告并记录方案
  -> 消费者查看报告并预约复评
  -> 品牌查看设备、门店和效果总览
```

Demo 新增的核心展示：

- 消费者：我的检测、报告详情、前后对比和复评入口。
- 门店：检测工作台、任务详情、模拟设备回传、报告解读和复评召回。
- 品牌：设备管理、检测运营、门店质量和效果总览。
- 演示控制：正常完成、离线重试、重复回传、数据不完整和设备门店不匹配。

所有页面明确标记为演示数据。P2 统计只展示概念和固定样例，不宣称来源于真实顾客、真实设备或真实效果研究。

## 12. 分期实施

### 12.1 P0：设备接入与可信档案

- 完成设备协议、身份认证、任务编排和回传网关。
- 完成会员、临时档案、授权、合并和门店隔离。
- 完成不可变原始归档、指标标准化、基础报告和审计。
- 完成设备与任务的主要异常处理。

P0 的目标是开始积累可信、可追溯的数据，而不是追求复杂分析。

### 12.2 P1：门店经营闭环

- 完成顾客时间线、前后对比、方案推荐和复评预约。
- 完成门店成交跟进、复评召回和设备利用率。
- 完成品牌设备管理、门店质量与基础效果看板。

P1 的目标是让门店愿意持续使用，并形成检测、成交和复评闭环。

### 12.3 P2：品牌数据资产

- 接入使用依从性。
- 完成产品、方案、周期和依从性分层分析。
- 完成跨设备偏差治理、异常预警和去标识化研究数据集。
- 数据量、指标标准和合规条件满足后，再评估影像算法、效果预测和智能推荐。

## 13. OpenSpec 拆分建议

该范围包含多个可独立验收的子系统，不应放入一个超大变更。建议依次建立：

1. `integrate-assessment-device-gateway`：设备、任务、回传、安全、幂等和原始归档。
2. `add-assessment-records-and-reports`：顾客档案、授权、标准化指标、报告和版本。
3. `add-assessment-store-workflow`：门店工作台、报告解读、成交跟进和复评召回。
4. `add-assessment-brand-operations`：设备运营、门店质量、异常线索和基础分析。
5. `extend-franchise-h5-assessment-demo`：使用本地数据模拟三端核心演示链路。

每个变更分别维护 proposal、spec delta、design 和 tasks，并在实施前验证依赖变更已完成。

## 14. 合规、安全与人文边界

- 体态指标和影像按敏感个人信息处理，传输和存储加密，密钥独立管理。
- 设备本地缓存同样按敏感个人信息保护，服务端确认接收后按数据保留策略清除。
- 检测、影像、运营联系、研究和宣传用途分别记录授权，不合并成模糊总授权。
- 门店只访问本店顾客；品牌访问遵循最小权限和必要性。
- 原始影像访问、下载、复核和导出比普通指标使用更严格的权限与留痕。
- 研究导出必须去标识化，并与日常经营导出分开审批。
- 顾客可以查看档案、授权范围和报告版本，并按适用规则申请导出或删除。
- 页面同时使用文字、数字和颜色表达变化，不依赖颜色判断好坏。
- 报告使用“体态记录、变化、建议关注”等非医疗表述，不制造焦虑，不承诺疗效。
- 医疗器械分类、门店资质、伦理审查和研究用途仍由法务、注册及专业顾问确认。

## 15. 正式接入前置条件

设备厂商或甲方必须提供：

- 完整接口文档和版本策略。
- 指标字段、单位、精度、参考范围和计算方式。
- 成功、失败、缺失和异常样例载荷。
- 原始影像格式、尺寸、编码、上传方式和文件校验规则。
- 设备身份认证、签名、防重放和密钥轮换方式。
- 断网缓存、重试、超时、重复提交和回执规则。
- 设备编号、门店绑定、软件版本和校准信息能力。
- 测试设备、联调环境和厂商技术联系人。

同时需要业务方完成上位设计中的四项确认：客观指标、医疗表述红线、门店专业资质和知情同意范围。

## 16. 验收标准

### 16.1 数据关联与一致性

- 每条有效结果均可追溯到顾客、任务、门店、设备、操作人和协议版本。
- 设备不依赖姓名或手机号进行结果归属。
- 重复回传不生成重复检测档案。
- 多次检测尝试只确认一份有效结果，失败尝试仍可审计。
- 临时档案合并后，检测、授权、报告和审计记录完整保留。

### 16.2 数据可信度

- 原始载荷与影像不可覆盖。
- 标准化指标、人工复核和报告具备独立版本。
- 缺失、超范围和设备门店不匹配的结果不自动生成正式报告。
- 规则升级后可以重新生成报告，并可查看旧版本。

### 16.3 权限与合规

- 门店无法访问其他门店顾客明细。
- 未授权的影像、研究和宣传用途被阻断。
- 查看、复核、合并、导出和规则变更均有审计记录。
- 顾客报告不包含诊断、治疗、矫正或疗效承诺。

### 16.4 Demo

- 能连续演示预约、任务、模拟设备回传、报告、方案、复评和品牌总览。
- 正常、离线重试、重复回传、数据不完整和设备门店不匹配均有明确结果。
- 三端读取同一份本地演示状态，流程变化实时联动。
- 一键重置后恢复确定性初始数据。
- 页面明确说明设备和效果数据为演示内容。

## 17. 可行性与主要风险

业务闭环在技术上可行，但正式周期主要受设备厂商接口成熟度、指标标准化和合规决策影响，而不是页面开发速度。

主要风险：

- 厂商只提供结果展示而不提供稳定结构化协议。
- 不同设备或软件版本对同一指标的计算口径不同。
- 设备断网和重复回传造成任务状态与设备状态不一致。
- 临时顾客身份处理不严导致错绑或错误合并。
- 门店业绩压力导致不规范操作或选择性录入。
- 未完成独立授权就积累影像和研究数据，造成历史数据不可用。
- 在样本和专业验证不足时上线智能推荐，形成合规和信任风险。

因此首期优先级必须是任务关联、原始数据、版本、审计和门店可执行流程，不能先做复杂图表或智能结论。
