# Apache-2.0 商业发行一致性设计

## 背景与前提

项目根目录 `LICENSE` 是 Apache License 2.0，`README.md` 同时声明“免费商用、无隐藏费用或功能限制”。但当前源码、安装器、后台和在线升级中仍存在另一套限制性许可与商业授权机制，包括：

- `crmeb/LICENSE.txt` 和安装协议限制删除版权标识、限制破坏商业授权机制；
- 自有源码头声明“并不是自由软件”；
- 后台首页和“商业授权”页面会请求 CRMEB 授权服务，并在本地写入授权码；
- 安装 SQL、升级内嵌清单、文件树和多语言文本保留授权接口及授权文件；
- 管理端、客服端和商城端在未配置品牌时强制显示 CRMEB 文案、链接或图片；
- 在线升级服务在构造阶段即认证，打开页面便可能向外部发送域名、主机和版本信息。

本设计以用户确认的发行规则为前提：根目录 Apache-2.0 是本项目的唯一软件许可。该前提是项目所有者的发行决定，不构成对上游权属的独立法律判断。Apache-2.0 要求保留的版权、作者和第三方依赖许可仍然保留；Apache-2.0 不授予上游商标权，因此不得把上游作者归属改写为天俪原创。

## 目标

- 删除与 Apache-2.0 免费商用规则冲突的软件使用限制和商业授权门槛。
- 彻底移除商业授权的前后端接口、自动请求、购买入口、种子数据和遗留升级客户端。
- 保留普通登录鉴权、角色权限、微信 OAuth、支付、短信、物流等正常业务或可选外部服务。
- 将原“商业授权”页面收敛为纯本地“系统信息”页面，并保持已有角色对菜单 ID `605` 的访问关系。
- 保留站点自定义版权/品牌能力，改用中性配置名；无配置时不显示 CRMEB 兜底。
- 官方远程升级默认关闭，关闭时任何页面和后端服务都不得向官方升级域名发请求；本地跨版本升级、备份和回滚保持离线可用。
- 新安装和现有数据库都能幂等清理授权残留，不修改商品、用户、订单、上传文件或示例数据。
- 源码与实际发布的管理端/H5 构建产物保持一致。

## 非目标

- 不删除普通安全鉴权、菜单权限码体系或管理员登录令牌。
- 不绕过官方升级服务器在显式启用远程升级后的认证或升级包资格规则。
- 不删除短信、物流、云存储、支付、微信等与软件许可无关的可选服务。
- 不清理上游作者、版权声明、Apache-2.0 要求的 NOTICE/许可证或第三方依赖许可证。
- 不借本次变更重构商城业务、修改示例数据或升级依赖版本。

## 设计决策

### 1. 统一许可文本，同时保留归属

保留根目录完整 Apache-2.0 文本。`crmeb/LICENSE.txt` 改为与根许可一致的 Apache-2.0 文本或明确指向根许可的等价副本；安装器只要求确认 Apache-2.0 和免责声明，不再加入额外商业限制。

项目自有源码中统一把“并不是自由软件，未经许可不能去掉版权”替换为 Apache-2.0 指引。原有 CRMEB copyright 和 author 行保留，因为它们是来源归属，不是运行时授权门槛。第三方和 `vendor/` 文件不做批量改写。

批量变更必须由可审计脚本按精确旧文本执行，并输出受影响文件清单。任何文件完整性清单中的对应 MD5 需要按最终文件重新生成，不能留下必然误报的旧哈希。

### 2. 删除商业授权执行链

删除 `SystemAuthServices`、`Common::auth()`、`Common::auth_apply()` 和 `check_auth`、`auth_apply`、`auth` 路由。管理端删除相应 API 包装、首页自动探测、商业购买 iframe、授权码、价格和申请逻辑。

被删除端点应返回 404，而不是返回伪造的“已授权”。这样既不保留门槛，也不伪装官方服务结果。

旧的 `SystemUpgradeClient`、`crmeb\services\UpgradeService` 和 `UpgradeOpenApiService` 未被当前路由使用，且会发送站点信息或检查域名升级权限，整体删除并同步文件树、安装 SQL 和升级内嵌清单。

### 3. 保留纯本地系统信息页

将 `pages/system/auth` 重命名为 `pages/system/info`，组件和 API 方法使用 `system_info`、`getSystemInfo` 等中性命名。页面保留现有 `system/info` 环境诊断，并提供只读写本地 `/copyright` 接口的站点品牌设置区；它不读取授权、商品价格、授权订单或外部 iframe。

初始化菜单和现有数据库都保留菜单 ID `605`，原地把 URL、`unique_auth`、标题和说明迁移为“系统信息”。角色关联依赖菜单 ID，保留 ID 可避免已有角色丢权；迁移后清理菜单缓存。浏览器标题、标签页、面包屑和搜索菜单均不得出现“商业授权”。

### 4. 品牌配置中性化

`/copyright` 继续作为商城启动接口返回业务 `status=200`，避免破坏现有运行时验收和客户端启动流程。配置键从 `nncnL_crmeb_copyright`、`nncnL_crmeb_copyright_image` 迁移为 `site_copyright_text`、`site_copyright_image`，API 响应字段暂时保持 `copyrightContext`、`copyrightImage` 以兼容已发布客户端。

现有数据库迁移只重命名这两个配置键并保留值。管理端 API 符号改为 `getSiteBranding`、`saveSiteBranding`；服务端、PC、客服和商城消费者统一读取新键。

未配置品牌文字或图片时，各端渲染空状态或站点名称/站点 Logo，不再回退到 CRMEB 官网链接、技术支持文案或 CRMEB 图片。只被这些兜底使用的品牌图片应删除或替换为中性占位，并先确认没有其他业务引用。

### 5. 官方远程升级显式启用

在 `config/upgrade.php` 增加 `official_remote_enabled`，由 `UPGRADE.OFFICIAL_REMOTE_ENABLED` 读取，默认 `false`；Docker 示例配置明确保留默认关闭。

`UpgradeServices` 构造函数只保存 DAO，不读取请求域名、不组装远程参数、不认证。所有官方远程方法先执行同一服务端门禁；关闭时返回明确的“官方在线升级未启用”，且在门禁前不得调用 HTTP 客户端。认证和请求参数只在门禁通过后惰性初始化。

官方端点统一从 `config/upgrade.php` 读取 HTTPS URL。若运行环境无法验证官方 HTTPS 服务，则保持功能关闭并报配置错误，不降级到 HTTP。前端在线升级页先读取一个纯本地状态接口；关闭时显示本地说明，不自动调用升级状态、列表或协议接口。

本地跨版本升级方法不经过远程门禁，并继续支持离线检查、SQL 预览、备份、执行和回滚。远程升级日志也受同一门禁约束，关闭时不发送。

### 6. 新装数据与存量迁移

安装 SQL 删除商业授权 API 文档行、授权专用翻译、被删除文件的文件树/MD5 行，并更新菜单 ID `605`。`crmeb/LICENSE.txt` 和其他仍存在文件的完整性记录按最终内容更新。

提供单独、幂等、可审计的存量迁移，仅执行：

- 删除 `eb_system_route` 中 `check_auth`、`auth_apply`、`auth` 三个商业授权 API 元数据；
- 删除 `eb_system_config.menu_name = 'cert_crmeb'`；
- 原地更新菜单 ID `605` 的系统信息路径、权限码和标题；
- 将两个旧版权键重命名为新的站点品牌键，并在目标键已存在时保留目标值、删除旧重复键。

脚本使用实际表前缀参数或升级框架的 `@table` 约定，不写死生产表名。迁移前后记录受影响行数；不得使用 `TRUNCATE`，不得触碰商品、订单、用户、上传或示例数据表。

### 7. 源码和构建产物同验收

管理端源码构建到 `template/admin/dist` 后，再按项目现有发布流程同步到 `crmeb/public/admin`。同步必须根据新 manifest/入口引用删除已失去引用的旧哈希 chunk，不能仅覆盖后留下包含商业授权代码的旧文件。

uni-app/H5 按项目现有构建链重建。若当前仓库没有可复现的 uni-app CLI 构建，则必须明确记录未重建的目标及原因，不能把源码扫描当作产物验证。

## 错误处理

- 官方在线升级关闭时返回稳定的业务错误和本地状态，不尝试联网，也不把关闭描述为“域名未授权”。
- 显式启用但配置缺失时提示“升级服务配置缺失”；认证失败提示“升级服务认证失败”；资格不满足时明确指向“官方升级服务资格”，不影响商城其他功能。
- 品牌配置接口失败时客户端不显示上游品牌兜底；它可以隐藏版权区域，但不得伪造配置。
- 数据库迁移在事务中运行；任何目标不唯一或 SQL 错误均回滚，并输出精确失败项。

## 验证策略

1. 先增加静态合规测试并确认在当前代码上失败，覆盖限制性许可、商业授权路由/服务/UI、旧配置键、旧菜单路径和构建产物。
2. 增加远程升级门禁测试，证明默认配置下构造服务及访问在线升级页均不会调用 HTTP 客户端；本地跨版本方法仍可离线执行。
3. 增加安装 SQL/存量迁移测试，使用最小临时表夹具验证幂等、菜单 ID 保留、品牌值保留和业务表示例数据不变。
4. 运行 PHP 语法检查、聚焦后端测试、管理端构建、可用的 uni-app/H5 构建和 `openspec validate align-apache-commercial-distribution`。
5. 在本地登录后台，验证首页、系统信息、品牌有值/空值、在线升级关闭态和跨版本升级；记录浏览器网络请求，确认无授权/升级域名请求。
6. 运行现有 runtime acceptance，确认 `/copyright`、主题、首页布局和语言接口仍返回业务 `status=200`，商品、订单和示例数据快照未变化。
7. 对源码和实际发布目录执行最终否定清单扫描；历史规格文档、第三方许可证和必要来源归属单独排除并人工复核。

## 风险与回滚

- 大量源码头变更会产生宽 diff，也会使旧 MD5 清单失效。通过精确文本脚本、变更文件清单和清单重生成控制风险。
- 菜单权限码改名可能受缓存影响。迁移保留 ID `605` 并在部署步骤中清理菜单/权限缓存。
- 旧客户端仍依赖 `/copyright` 字段。保持响应字段兼容，只中性化内部键和前端符号。
- 官方升级服务 HTTPS 可用性未知。默认关闭是安全状态；不允许自动回退明文 HTTP。
- 回滚时可恢复旧代码和菜单/配置键，但商业授权端点与限制性许可不会作为业务数据恢复。数据库和上传数据不参与本次变更，仍由既有快照保护。
