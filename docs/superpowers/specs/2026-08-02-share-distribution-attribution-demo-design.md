# 分享分销归因 Demo 设计

## 背景

当前 H5 Demo 已分别提供分享中心、推荐有礼、分销中心、订单分账和提现审核，但这些模块尚未形成业务闭环：分享只记录预设访问量和转化数；新订单固定展示 5% 分销成本，却没有分享来源、推荐关系或佣金记录；现有佣金明细全部来自种子数据。

本次改造把这些独立模块连成可现场演示的本地假业务链路：

```text
生成分享 -> 好友打开 -> 接受推荐 -> 下单支付 -> 生成佣金
         -> 首单推荐奖励 -> 品牌完成分账 -> 佣金可提现 -> 品牌审核提现
```

## 目标

- 分享中心生成带唯一令牌的真实链接和二维码。
- 模拟好友通过落地页接受推荐并形成持续绑定关系。
- 归因订单按分销员档案中的 8% 比例生成待结算佣金。
- 好友首单同时发放一次 8 元推荐奖励。
- 品牌完成订单分账时同步结算佣金并增加可提现余额。
- 分销员提交提现后复用现有品牌审核和到账流程。
- 全链路继续使用确定性本地状态，可重置、可重复演示。

## 非目标

- 不接入微信 JS-SDK、微信授权、真实社交分享或渠道回流。
- 不接入真实登录、支付、数据库、CRMEB API、银行卡或支付宝。
- 不实现多级分销、跨设备实时同步、归因有效期或复杂归因竞争规则。
- 不改变正式 CRMEB 商城、管理后台、容器运行时或数据库结构。

## 已确认的业务规则

1. 好友从模拟落地页主动点击“接受推荐并进入商城”后完成绑定。
2. 推荐关系持续有效，后续订单继续归属于同一分销员。
3. 分销佣金按订单实付金额乘以分销员档案的 8% 比例计算，按分取整。
4. 首单推荐奖励为 8 元，只发放一次，与分销佣金分开统计。
5. 分销成本由品牌佣金承担，不减少门店应得收入。
6. 佣金随关联订单分账完成而结算，不设置独立佣金结算动作。
7. 没有有效分享归因的普通订单不产生分销佣金。

## 方案选择

采用“分享令牌 + 本地归因状态”方案。

每次分享生成唯一令牌和分享记录。链接携带令牌，落地页只通过令牌查询推荐人、门店和分享内容，不直接信任 URL 中的分销金额或比例。好友接受推荐后，本地状态保存持续归因关系；订单支付时从该关系生成订单来源、佣金记录和首单奖励。

该方案比在 URL 中直接携带分销员编号更适合演示，因为它能准确关联一次分享的访问、绑定、订单和佣金；也比一键生成订单的场景生成器更接近实际业务过程。

## 状态模型

本地数据版本从 `7` 升到 `8`，触发旧浏览器状态恢复为新的固定示例数据。原有商品、服务、预约、检测、直播和订单示例继续保留。

### 分享记录

扩展 `shareRecords`：

```js
{
  id,
  token,
  distributorId,
  storeId,
  contentType,
  contentId,
  content,
  channel,
  visits,
  bindings,
  orders,
  createdAt,
}
```

历史分享记录允许没有令牌；只有新生成且带令牌的记录可进入归因链路。

### 推荐绑定

新增 `distributionBindings`：

```js
{
  id,
  shareId,
  token,
  distributorId,
  referralId,
  customerId,
  customerName,
  phone,
  storeId,
  status: 'active',
  acceptedAt,
  firstOrderId: null,
}
```

同一模拟消费者只能保留一个有效分销绑定。重复接受同一令牌返回已有绑定，不重复增加绑定数或推荐记录。

本地状态同时保存 `visitedShareTokens`，同一浏览器对同一令牌只增加一次访问量，刷新落地页不重复计数。

### 订单归因

归因订单增加：

```js
{
  distributionAttribution: {
    shareId,
    bindingId,
    distributorId,
    referralId,
    commissionRate,
  },
  distributionCostCents,
}
```

无归因订单的 `distributionAttribution` 为 `null`，`distributionCostCents` 为 `0`。既有种子订单可保留其演示金额，但新增订单必须遵守该规则。

### 佣金记录

扩展 `commissionRecords`：

```js
{
  id,
  orderId,
  shareId,
  bindingId,
  distributorId,
  customerName,
  commissionRate,
  amountCents,
  status: 'pending' | 'settled',
  at,
  settledAt,
}
```

订单与佣金记录按 `orderId` 一对一约束，重复支付或重复状态推进不得重复生成或结算佣金。

## 状态流

### 1. 生成分享

分享中心选择门店、商品或预约内容后生成一条分享记录，初始访问、绑定和订单计数均为零。页面展示可下载二维码、复制链接和“模拟好友打开”入口。

### 2. 接受推荐

好友落地页根据令牌显示推荐人“陈女士”、门店和分享内容。点击接受后：

- 分享访问量在首次打开时增加一次；
- 创建待首单推荐记录；
- 创建持续分销绑定；
- 分享绑定数增加一次；
- 进入对应门店首页。

无效令牌显示“分享链接无效”，提供返回门店首页的操作。重复打开或接受同一令牌展示已有绑定，不重复写入状态。

### 3. 归因下单

好友完成模拟支付后：

- 订单记录分享、绑定、推荐和分销员来源；
- 按实付金额的 8% 创建待结算佣金；
- 分销员累计佣金和待结算佣金同步增加；
- 分享订单数增加一次；
- 若绑定尚无首单，则推荐记录变为“已奖励”，发放 8 元推荐奖励并记录首单订单号；
- 后续订单继续产生 8% 佣金，但不再发推荐奖励。

同一 `paymentAttemptId` 重复支付时直接返回原订单，不重复修改以上数据。

### 4. 分账结算

品牌方把关联分账记录推进到“已完成”时：

- 找到同一订单的待结算佣金；
- 佣金状态改为“已结算”；
- 分销员待结算金额减少；
- 已结算金额增加；
- 可提现余额随选择器结果同步增加。

重复推进已完成分账不重复处理佣金。

### 5. 提现审核

分销中心复用现有提现申请表单。申请金额不得超过已结算金额扣除未驳回提现后的余额。品牌方继续使用现有两阶段审核：待审核 -> 处理中 -> 已到账，或直接驳回。

## 页面改造

### 消费者端

- 分享中心：生成令牌化分享记录，展示真实链接、二维码、复制和模拟好友打开操作。
- 新增分享落地页：展示推荐人、门店、分享内容和接受推荐按钮。
- 确认订单页：有效绑定时展示“推荐关系已绑定”。
- 支付成功页：归因订单展示“本单已计入分享归因”。
- 推荐有礼：首单后推荐记录从“待首单”变为“已奖励”。
- 分销中心：新增订单佣金后立即刷新累计、待结算和佣金明细。

### 品牌端

- 全平台订单：展示是否为分享归因订单及推荐人。
- 分账详情：展示分销员、佣金比例、佣金金额和结算状态。
- 分销管理：展示分享访问、绑定人数、成交订单、待结算和已结算佣金。
- 提现审核：继续支持门店和分销员申请的通过、到账和驳回。

## 实现边界

- 分享链接使用当前页面的 `origin`、部署子路径和 hash 路由动态生成，部署到 `/franchise-demo/` 后二维码不得包含 `127.0.0.1`。
- 归因、订单、佣金、结算和提现使用现有 `demoStore.commit` 与转换函数，不在页面组件中直接拼接财务状态。
- 金额统一使用整数分；佣金使用 `Math.round(paidCents * commissionRate / 100)`。
- 推荐奖励只更新推荐统计，不并入分销佣金或可提现余额。
- 重置演示数据恢复确定性的版本 `8` 种子，不保留浏览器里的临时绑定。

## 异常与幂等

- 未找到分享令牌：不创建绑定，显示无效链接。
- 分享记录缺少分销员或门店：视为无效链接。
- 重复接受同一令牌：返回已有绑定。
- 已存在其他有效绑定：继续使用首次有效绑定，不静默覆盖。
- 普通订单：不生成佣金。
- 重复支付请求：不重复生成订单、分账、积分、佣金或推荐奖励。
- 重复完成分账：不重复结算佣金。
- 提现金额超过可提现余额：拒绝申请且不新增记录。

## 测试与验收

### 单元测试

- 分享令牌生成、链接解析和无效令牌。
- 接受推荐的绑定、推荐记录和重复接受幂等。
- 普通订单不分佣，归因订单按 8% 生成一条待结算佣金。
- 重复支付不重复发佣金、积分或首单奖励。
- 首单发 8 元推荐奖励，后续订单仅继续分佣。
- 分账完成同步结算佣金并增加可提现余额。
- 提现申请、余额冻结、审核、到账和驳回。
- 分享、分销和品牌汇总选择器保持金额与数量一致。

### 页面与 E2E

- 分享中心生成二维码并可进入好友落地页。
- 好友接受推荐后在确认订单页看到绑定提示。
- 完成下单后，支付成功页、推荐有礼和分销中心同步更新。
- 品牌订单和分账详情显示分享归因与 8% 佣金。
- 品牌完成分账后，分销员可提现余额增加。
- 分销员申请提现，品牌审核至已到账。
- 完整链路刷新后仍由本地存储保持，重置后恢复版本 `8` 示例数据。

## 成功标准

甲方可在同一浏览器中完整操作并观察以下因果关系：分享链接产生绑定，绑定订单产生 8% 佣金和一次 8 元首单奖励，订单分账完成使佣金可提现，提现申请由品牌审核并模拟到账。所有金额、状态和汇总在消费者、门店和品牌页面保持一致，且任何重复操作不会产生重复收益。
