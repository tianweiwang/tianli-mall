# 天俪加盟门店平台 H5 Demo 设计

**状态：** 已确认，待实施计划

**日期：** 2026-07-30

## 1. 背景与目标

基于当前 CRMEB 正式商城端和管理后台的 UI 体系，制作一套可独立部署的纯前端 H5 Demo，供甲方评审加盟门店平台的业务方向与操作流程。

Demo 展示三个角色：

- 消费者：从门店二维码进入对应子商城，完成商品下单和服务预约。
- 加盟门店：查看本店订单、预约、业绩和结算信息，并真实扫描二维码完成模拟核销。
- 品牌方：管理加盟门店、统一商品、全平台订单与预约，并查看抽成、分账和经营数据。

Demo 的成功标准不是接通生产能力，而是让甲方沿一条连续流程看懂：顾客属于哪家门店、门店如何接待和核销、品牌方如何统一管理和取得抽成。

## 2. 已确认原则

1. Demo 是独立前端工程，不改 CRMEB 正式前后台业务代码。
2. 消费者端采用全屏移动 H5，不使用手机外框；手机打开即为标准商城界面。
3. 门店端和品牌方后台采用桌面管理后台布局。
4. 视觉沿用当前正式项目，并对新页面做克制的细节优化。
5. 商品图片与示例内容优先复用当前商城数据和素材。
6. 不接真实 API、数据库、支付、微信授权或生产核销服务。
7. 三个角色在同一浏览器内通过本地状态联动，并支持一键重置。
8. 二维码必须真实生成、真实可扫描；二维码承载的业务数据为 Demo 数据。
9. `docs/prototype` 不作为视觉、结构或代码参考。

## 3. 范围边界

### 3.1 包含

- 三角色完整演示入口和快速切换。
- 门店扫码归属。
- 集团统一商品下单。
- 模拟微信支付与订单状态流转。
- 服务预约、容量占位、取消和到店核销。
- 门店订单、预约、统一商品、业绩和结算页面。
- 品牌方门店、商品、订单、预约、分账和经营分析页面。
- 正常、跨店、重复、过期四类核销结果。
- 浏览器本地状态持久化和演示数据重置。
- 摄像头扫描、二维码图片识别和权限失败降级提示。

### 3.2 不包含

- 真实账号登录、角色权限和密码找回。
- PHP、MySQL、Redis 或任何远程 Mock API。
- 真实微信支付、退款、分账、商户进件和订阅消息。
- 真实地图定位、文件上传和微信登录。
- 生产级二维码签名、防伪、防重放和跨设备实时同步。
- 正式商城代码迁移、数据库迁移或现有接口改造。
- 完整多商户能力，例如门店自建商品、独立库存、拆单和自主发货。

## 4. 技术架构

### 4.1 工程形态

在仓库内建立独立目录：

```text
demo/franchise-platform-h5/
```

工程使用与当前后台相近的 Vue 2、Vue Router 3 和 Element UI 2 技术组合。消费者页面使用项目内自有 Vue 组件和样式，避免为移动端引入第二套重量级 UI 框架。

构建结果为一套静态资源。Vue Router 使用 hash 模式，保证部署在任意 Nginx 子目录时，刷新页面不依赖服务端路由回退。构建公共路径使用相对路径。

### 4.2 模块边界

```text
src/
  assets/             当前商城筛选后的图片、图标和字体
  components/
    customer/         消费者端商品、订单、预约组件
    admin/            后台导航、统计、筛选、表格组件
    demo/             角色切换、状态提示、重置控制
    qr/               二维码生成、扫描和结果组件
  layouts/
    CustomerLayout    移动 H5 全屏布局
    StoreLayout       门店后台布局
    BrandLayout       品牌方后台布局
  mock/
    seed.js            可重复初始化的演示数据
    store.js           状态读取、写入、重置和迁移
    transitions.js     订单、预约、核销、分账状态流转
  router/
  views/
    customer/
    store/
    brand/
    verify/
```

页面只通过 `mock/store.js` 读取和修改状态，不允许组件直接操作 `localStorage`。状态流转集中在 `transitions.js`，避免不同页面各自伪造业务结果。

### 4.3 演示状态

本地状态以带版本号的单一 JSON 文档保存：

```text
demoState
  version
  activeRole
  activeStoreId
  stores
  products
  services
  slotInventory
  cart
  orders
  bookings
  profitSharingRecords
  activityLog
```

初始化数据包含 3 家加盟门店、当前商城代表商品、多个预约服务和覆盖不同状态的订单、预约、分账记录。所有姓名、手机号、证件、商户号和财务信息均为明确的模拟数据。

状态版本不匹配或内容损坏时，应用自动恢复种子数据并给出友好提示。重置操作需二次确认，重置后回到消费者门店首页。

## 6. 主演示流程

### 6.1 商品订单链路

1. 使用真实门店二维码打开指定门店商城。
2. 首页显示当前门店，并将归属写入本地状态。
3. 选择商品、规格和数量，加入购物车。
4. 确认订单并执行模拟微信支付。
5. 生成已支付订单，固化门店归属、品牌抽成和门店预计收入。
6. 切换门店端，本店订单和业绩指标增加。
7. 切换品牌方后台，订单和待分账流水出现。
8. 在分账详情中推进模拟分账状态并展示资金拆分。

商品由集团统一配送，因此门店端只能查看订单，不出现发货动作。

### 6.2 服务预约链路

1. 从门店首页进入服务预约。
2. 选择服务、日期和有余量的时段。
3. 提交后占用本地时段容量并生成待到店预约。
4. 预约详情显示真实二维码和备用核销编号。
5. 切换门店端，使用摄像头或二维码图片完成扫描。
6. 系统校验门店与状态，确认后将预约改为已核销。
7. 门店预约列表、工作台和品牌方预约统计同步更新。

预约不创建订单、不发起支付。到店后的实际交易属于正式系统未来业务，本 Demo 只展示预约到店和核销。

## 7. 二维码设计

### 7.1 门店入口码

门店入口码编码当前部署地址和门店编码，例如：

```text
https://demo.example.com/#/c/store/TL1001
```

消费者扫码后进入指定门店，并更新当前门店归属。切换门店码后，新订单和新预约归属新门店，历史记录不变。

### 7.2 订单与预约核销码

核销码编码一个版本化的 Demo URL，载荷包含：

- 数据版本
- 业务类型
- 订单或预约编号
- 门店编号
- 必要的展示字段
- 签发时间
- Demo 校验值

载荷只包含模拟数据，不包含真实个人信息。校验值仅用于发现载荷损坏，不宣称具备生产防伪能力。

同一浏览器中，扫描器优先查找已有记录并执行状态流转。跨设备扫描时，扫描器可以根据二维码载荷导入一条 Demo 记录并完成本机核销，但消费者设备不会实时收到状态变化。页面应明确标记为演示环境，避免甲方把跨设备同步误认为已经实现。

### 7.3 扫描能力

- 使用成熟二维码生成库生成 Canvas 或图片二维码。
- 使用成熟浏览器二维码扫描库调用摄像头。
- 支持上传二维码图片作为无摄像头环境的降级方式。
- 摄像头权限被拒绝时，给出重新授权和图片识别入口。
- 核销确认前展示门店、预约人掩码、时段和当前状态。

## 8. 状态流转

### 8.1 订单

```text
待支付 -> 已支付 -> 配送中 -> 已完成
             |
             -> 退款中 -> 已退款
```

支付、配送和退款均由显式演示动作推进。订单一旦创建，门店归属不可修改。

### 8.2 预约

```text
待到店 -> 已核销
   |
   -> 已取消
   -> 已过期
```

取消和过期释放本地时段容量。重复释放不得使已预约数小于零。跨店、重复和过期核销均拒绝改变状态。

### 8.3 分账

```text
待分账 -> 处理中 -> 已完成
                    |
                    -> 回退中 -> 已回退
```

每条记录展示订单金额、门店预计收入、品牌抽成和由品牌承担的分销佣金。演示数据必须满足：门店收入 + 品牌抽成 = 订单实付金额，分销佣金从品牌抽成中列示，不从门店收入再次扣除。

## 9. 视觉设计

### 9.1 消费者端

- 沿用当前商城红色主色、白色内容区和浅灰页面背景。
- 复用当前商品图片、分类图标、价格样式和底部导航语言。
- 卡片圆角控制在现有设计尺度内，不做营销落地页式大标题和装饰性背景。
- 首屏通过门店名称、位置和营业状态明确当前归属。
- 手机视口全屏展示；桌面打开时限制内容阅读宽度，但不绘制手机边框。

### 9.2 后台

- 沿用 CRMEB 左侧菜单、顶部栏、面包屑、筛选区、表格和表单样式。
- 统计信息保持紧凑，避免卡片嵌套和大面积装饰。
- 门店端与品牌后台通过菜单内容和页面标题区分，不创建完全不同的主题。
- 金额、分账状态、异常状态使用语义色，不用单一红色承载全部信息。

### 9.3 可用性

- 正文和关键控件满足基本对比度。
- 表单、按钮和二维码操作提供明确状态反馈。
- 错误提示说明如何恢复，不责怪用户。
- 后台支持键盘焦点和常用表格筛选操作。
- 二维码之外始终提供可复制的核销编号，作为无障碍降级路径。

## 10. 异常与边界场景

- 无门店参数进入：使用默认演示门店，并提示当前归属。
- 门店参数不存在或停用：展示不可用状态并允许选择其他门店。
- 购物车已有其他门店商品：提示切换门店将清空当前购物车，确认后执行。
- 时段已满：禁止提交，并引导选择其他时段。
- 重复下单动作：按钮进入处理中状态，防止生成两条记录。
- 摄像头不可用：提供二维码图片识别和备用编号。
- 跨店核销：显示预约所属门店和当前操作门店，不改变记录。
- 重复或过期核销：显示原状态和时间，不重复写入业绩。
- 本地数据损坏：恢复种子数据，并说明演示数据已重置。

## 11. 部署设计

构建输出目录为静态 `dist/`，可部署到独立域名或 Nginx 子目录。由于使用 hash 路由，不要求 PHP，也不要求额外的 `try_files` 配置。

部署应满足：

- HTTPS。摄像头能力在正式浏览器中通常要求安全上下文。
- 静态资源使用相对路径，支持子目录部署。
- 所有图片、字体和脚本随构建产物交付。
- 不引用临时开发服务器、外部 Mock 服务或当前 `8011` 接口。
- Demo 与现有 `8011` CRMEB 服务使用不同地址，不覆盖正式演示环境。

## 12. 验收标准

### 12.1 功能

- 能从门店二维码进入正确门店商城。
- 能完成商品加入购物车、确认订单和模拟支付。
- 新订单能在同一浏览器的门店端和品牌后台出现。
- 能选择预约时段、占用容量并生成真实二维码。
- 门店端能通过摄像头或图片识别真实二维码。
- 正常、跨店、重复、过期四种核销结果符合设计。
- 门店业绩、品牌抽成和分账数据随演示动作更新。
- 重置后所有数据恢复到相同种子状态。

### 12.2 数据一致性

- 历史订单和预约不会因切换当前门店而改变归属。
- 门店端看不到其他门店明细。
- 门店收入与品牌抽成之和等于订单实付金额。
- 分销佣金由品牌抽成承担，不从门店收入中重复扣除。
- 取消和过期后，时段已预约数量准确回退且不会小于零。

### 12.3 浏览器与视觉

- 消费者端至少验证 375x812、390x844、430x932 三个移动视口。
- 后台至少验证 1280x800 和 1440x900 两个桌面视口。
- 页面无横向溢出、文字遮挡、空白主区域和布局跳动。
- 浏览器控制台无未处理异常。
- 构建产物在不连接 CRMEB API 的情况下可完整运行。
- 生成的门店码和核销码能被实际二维码解码器识别。

### 12.4 演示验收链路

最终验收按以下顺序完整执行：

```text
扫码进入门店
  -> 商品下单
  -> 模拟支付
  -> 服务预约
  -> 展示核销码
  -> 门店真实扫描核销
  -> 查看门店业绩
  -> 品牌查看抽成与分账
```

验收结束后执行一次演示数据重置，确认下一次演示可从相同初始状态开始。

## 13. 实施约束

- 实现阶段先建立共享模拟状态和状态机，再开发页面，避免先堆静态页面后补联动。
- 页面和组件只实现本设计列出的范围，不扩展真实后台能力。
- 从正式项目复制素材时保留来源记录，仅复制 Demo 使用的最小集合。
- 不读取或打包正式环境密钥、`.env`、`.constant`、上传隐私数据或数据库导出。
- 任何看起来像真实支付、真实分账或生产二维码安全能力的界面，都必须使用明确的演示状态和模拟数据。
