# 实施规格：现有 CRMEB 改造为多商家商城 v0.1

文档版本：1.0（由草稿 v0.3 整理，并写入 2026-10-11 的 D2/D3 决策）。决策编号见 [README.md](README.md) §3。

## 1. 范围

### 1.1 首版做什么

- 一个平台、多家独立商家；一家商家对应一家线上店铺。
- 平台人工建立和审核商家，不做公众自助入驻。
- 普通实物商品，快递履约。现有门店/提货点（`SystemStore`、`store_id`）保持原有含义，不升级成商家。
- 顾客账号全平台共用；商家只能看到本店订单履约所需的顾客信息。
- 购物车按商家分组展示；一次结算只能包含一家商家的商品；一笔订单只属于一家商家，分别支付。
- 商家处理本店的发货和售后；平台保留审核和有授权的介入能力。
- 平台后台与商家后台分开身份、接口和受保护操作，可以复用组件。

### 1.2 首版不做什么

- 跨店合并支付、充值余额、积分抵扣、优惠券、分销及其他活动叠加。这些是对**新交易入口**的服务端约束：不能只隐藏页面，也不能清空或遗弃存量余额、积分、进行中的活动。存量权益在 MS4 之前登记处理方式。
- 预约、检测、区域代理、定制会员、补贴；H5 Demo 不合并。
- 微服务拆分、全量依赖升级、换框架、整库重构。

### 1.3 工程原则

- 模块化单体，沿用现有 ThinkPHP 多应用 + `dao`/`services` 分层。
- 复用公共计算与履约逻辑；通过显式的授权服务、商家范围仓储和不同端的控制器建立边界；不复制整套业务服务形成长期分叉。
- 新增的商家 API 不得直接复用会返回全平台数据的管理端控制器。

## 4. 身份与认证

### 4.1 身份类型

| 身份 | 应用 | 令牌 type | 说明 |
|---|---|---|---|
| 平台管理员 | `adminapi` | `admin` | 跨商家操作需要明确权限并留审计 |
| 对外账号 | `outapi` | `out` | 第三方系统；MCP 入口不用 JWT，直接用 appid/appsecret 请求头 |
| 客服 | `kefuapi` | `kefu` | MS1 起商家令牌不得进入 |
| 顾客 | `api` | `api` | 全平台共用账号 |
| 商家员工 | `merchantapi`（MS1 新增） | `merchant` | 账号必须关联有效商家和员工状态 |
| 支付回调 | 各回调入口 | 无 | 靠支付机构签名和原支付记录定位，不依赖任何员工令牌 |
| 后台任务 | 队列/定时任务 | 无 | 由可信生产端携带业务归属，消费者重新建立范围并校验资源 |

### 4.2 通用规则

1. 接收端决定自己接受的令牌类型，不能按令牌自报的类型选择认证器。
2. 验签、算法与时间检查通过之前，不得使用载荷中的任何字段做身份选择或业务写入。
3. 每次受保护请求都要核对账号当前存在、未删除、已启用。
4. 认证失败不能产生业务副作用；允许的副作用只有安全审计和限流计数。
5. 错误应用中的认证失败，不能删除该令牌在其正确应用里的合法会话。
6. 签名密钥缺失或为 `default`、会话存储不是 Redis 时，相关认证能力拒绝工作，不能降级。

### 4.3 MS0a 认证契约（保留现有令牌格式）

现有 `JwtAuth::createToken` 在签发时会把 `{uid, type, token, exp}` 写入缓存（键为 `md5(token)`），这就是现有的会话白名单。MS0a 只把它**正确地验证起来**：

| 检查项 | adminapi | outapi |
|---|---|---|
| 验签（固定 HS256）与时间 | 先于一切载荷使用 | 先于一切载荷使用 |
| 载荷 type | 必须为 `admin` | 必须为 `out` |
| 缓存白名单记录 | 必须存在，且 `type`、`uid` 与令牌一致，`token` 与请求令牌完全一致 | 同左（`type` 为 `out`） |
| `pwd` 声明 | 必须存在，且等于 `md5(当前管理员 pwd 字段)` | 不要求 |
| 当前账号 | 存在、`is_del = 0`、`status = 1` | 存在、`is_del = 0`、`status = 1` |
| 刷新 | 不涉及 | 刷新前后都按上面规则核对；只续签 `out` 类型 |
| 失败副作用 | 无业务写入；只有当白名单记录属于本应用且账号已失效时，才删除该记录 | 同左 |

对外账号的状态以管理后台开关为准：`1` 开启、`0` 关闭（数据库默认 `1`）。登录、访问、刷新、MCP 四个入口统一使用"`status = 1` 且 `is_del = 0` 才允许"。

客服（kefuapi）和顾客（api）端的签发方式在 MS0a 不改，但验证端补上同样的两项检查：载荷 type 必须分别为 `kefu`、`api`，缓存白名单记录的 `type`、`uid`、`token` 必须与令牌一致。原因是这两端目前都不检查 type（01 文档 F-26），后台或对外令牌的数字 ID 撞上时会被当成客服或顾客。客服/顾客令牌访问管理端（A13/A14）目前已被 `pwd` 比对拒绝，作回归保留。

### 4.4 MS0b 会话 v2 契约

MS0b 引入版本化会话。键结构与规则：

```text
auth:v2:<session_epoch>:<app>:account:<id>   -> session_version, blocked
auth:v2:<session_epoch>:<app>:session:<sid>  -> subject_id, type, audience, session_version,
                                                token_digest(SHA-256), credential_stamp, expires_at, status
```

- `<app>` 来自服务端固定枚举（`adminapi`、`outapi`，MS1 起加 `merchantapi`）。
- `session_epoch` 来自部署配置，所有实例一致；`sid`、`session_version` 至少 128 位安全随机数。
- 令牌载荷增加 `auth_schema=2`、`session_epoch`、`sid`、`session_version`、`iss`、`aud`；不再依赖 `pwd`。
- `credential_stamp` = HMAC(独立服务端密钥, 应用 + 主体 + 当前凭据摘要)，只存服务端。
- 账号键或会话键丢失时拒绝；只有凭据登录可以初始化账号版本；访问和刷新不得重建丢失的键。
- 退出撤销对应 `sid`；改密、停用、删除、应用密钥变更、全会话撤销会轮换账号版本。
- 凭据或状态变更顺序：先在 Redis 置 `blocked` 并轮换版本 → 再改数据库 → 数据库提交后解除 `blocked`。任一步失败保持保护状态，不报告成功。
- 刷新是单次兑换：同一旧 `sid` 只有一次刷新能成功；新会话写入成功之后才把新令牌返回给调用方；不恢复已消耗的旧 `sid`。
- Redis 中会话不存在返回未认证；Redis 或数据库故障返回受控不可用（503）。两种情况都不得进入业务控制器，也不得回退到文件缓存、进程内存、旧键或纯 JWT。
- 会话状态丢失或从旧快照恢复时：先隔离认证入口，轮换 `session_epoch`，再开放重新登录；禁止 `FLUSHALL`。
- 上线时旧 admin/out schema 一律拒绝，不回查旧的裸 `md5(token)` 键。发布前必须完成外部调用方清单与通知（见 §11.3）。

### 4.5 动作授权

- 认证之后再做动作授权，最高权限管理员也一样先过认证。
- 已登记（`eb_system_menus.auth_type = 2`）的接口按角色授权；**未登记的受保护接口默认拒绝**，只有显式白名单中的"已登录即可"接口例外。`crud/` 前缀不再整体放行。
- 权限缓存可以保留，但角色、菜单（接口登记）、白名单发生变更后必须清除受影响的缓存；验收看撤权后是否仍能操作。
- 响应：新接口区分 401（未认证）、403（无动作权限）、404（跨商家私有对象，不泄露存在性）。旧接口沿用 `{status, msg}` 业务码包装时，按业务码判断拒绝，并核对零副作用。

## 5. 商家上下文与查询范围（MS1 起）

### 5.1 MerchantContext

- 字段：`merId`（>0）、`employeeId` 或受控服务身份、已验证的动作权限、会话/权限版本、`requestId` 或 `jobId`。
- 只能由服务端在验证会话、员工归属、员工状态、商家状态之后创建。Header、请求参数、前端存储只能作为选择器，不能作为授权依据。
- 不放进 static 属性、全局变量、进程级单例，也不放进被容器复用的可变服务对象。优先显式传参；队列消费者每个任务重建，并在 `try/finally` 中结束作用域。
- 任务载荷里的 `mer_id` 不是授权凭证；消费者要核对任务来源、资源真实归属和当前允许的动作。

### 5.2 三种查询范围

| 范围 | 要求 | 禁止 |
|---|---|---|
| `MerchantScope` | 必须有有效 `MerchantContext`，`merId > 0` | 上下文缺失时查全表或回退到 0 |
| `PlatformScope` | 必须有平台动作权限；可指定目标商家，或做受审计的全局查询 | 靠缺省 `mer_id` 获得全局 |
| `PublicCatalogScope` | 只返回可公开字段；可全平台浏览，也可按店筛选 | 复用后台详情（返回成本价、备注等） |

`BaseDao` 的 `get`、`getCount`、`be`、`getOne`、`getColumn`、`delete`、`update`、`selectModel(search=false)` 都直接用模型查询，不经过 `search()`。商家范围必须由仓储/服务层强制，不能只改 `search()`，也不能给所有全局 DAO 盲加 `mer_id`。受保护的更新和删除，其 `WHERE` 条件本身要包含正确归属；批量操作混入他店 ID 时整批拒绝、零修改。

## 6. 数据归属（决策 D4、D7）

### 6.1 mer_id

- 唯一归属字段为 `mer_id`。上游安装结构中已有 `mer_id` 的表（见 01 文档 F-21）：`eb_article`、`eb_store_combination`、`eb_store_integral_order`、`eb_store_order`、`eb_store_product`、`eb_store_service`、`eb_store_service_log`、`eb_system_user_level`、`eb_user_level`。这些列默认值为 `0`，其中 `eb_store_product.mer_id` 的注释是"0 为总后台管理员创建"。
- `eb_system_log` 上有一个 `merchant_id` 列，含义待 MS2 盘点；不得把它当作商家归属，也不得新增其他 `merchant_id`。
- 是否沿用上述列，以 MS2 对真实数据库的只读 DDL 核对为准：同语义就复用；缺列则通过批准的增量迁移新增；语义冲突则停止并产出一次性映射方案。
- 自营商家是显式创建的正整数 ID。历史上 `mer_id = 0` 的数据，只有在确认归属后才迁到自营 ID；未知归属的数据隔离登记，并阻止多商家真实启用。
- 新的受保护写入必须由服务端写入可信的 `mer_id`；漏写时失败，不依赖数据库默认值 `0`。
- 客户端不能指定或修改归属；请求同时出现 `mer_id` 和 `merchant_id` 时拒绝。
- MS0a/MS0b 不改动任何商品归属数据。

### 6.2 资源归属

| 资源 | 归属 | 操作边界 |
|---|---|---|
| 商品分类主数据 | 平台全局 | 平台维护；商家只能选择启用的分类；首版不做店内分类树 |
| 商品与分类绑定 | 随商品 | 商家只改自己商品的绑定 |
| 商品、规格值、规格预设、库存流水 | 商家 | 规格必须属于同一商家的商品 |
| 运费模板及区域、包邮规则 | 商家 | 商品只能引用本家模板；不回退平台模板 `id=1` |
| 省市区、承运商字典 | 平台全局只读 | 商家只读 |
| 商品评价 | 作者是顾客；经营归属随原订单商品 | 商家只能看和回复本店评价，不能伪造、改原文、自删；平台审核并留审计 |
| 商品图片 | 管理权归商家，发布后可公开 | 可公开读取不等于素材库可以枚举、覆盖、删除 |
| 售后凭证、导出文件、商家资质 | 商家受保护 | 下载凭证限定身份、商家、期限 |
| 顾客账号、地址簿 | 顾客私有 | 商家只读本店订单的收货快照和必要售后信息 |
| 订单、订单项、售后、发货、资金记录 | 随订单商家 | 创建后归属不可修改；拆单 `pid` 树保持同一商家 |
| 客服会话、消息、附件 | 会话商家 + 顾客 + 有授权的客服 | 同一顾客在 A、B 店是两个授权范围 |
| 平台跨商家统计、审核 | 平台 | 明确授权并留审计 |

### 6.3 金额

保留现有以元计的精确金额字段和类型，禁止改成浮点或整体乘以 100。支付接口所需的分值转换要显式、精确并单独测试。

## 7. 商品发布与商家生命周期（MS2）

- 商品状态：草稿 → 待审核 → 已发布 / 驳回 → 下架。商家不能自行提交"已审核"；只改 `is_show` 不等于审核通过。
- 内容、规格定义或关键价格修改后，新版本停止销售并重新审核；已有订单使用下单快照。库存数量调整单独授权和记账，不触发内容重审。
- 商家状态分开控制：
  - **接新单开关**：关闭后下架新销售入口、禁止新建订单；首版默认不再发起新支付。
  - **履约权限**：仍可处理已付款订单、发货和售后。
  - **安全封禁**：撤销员工令牌，由平台受控接管存量履约。
  - **退出**：没有未完成的履约、退款、结算责任后才能关闭；不硬删除历史订单。
- 商家暂停后，晚到的支付成功回调仍要认证、入账，并进入既定的履约或退款流程。

## 8. 单店交易（MS4）

- 一次提交的商品必须全部属于同一个可交易商家。归属由服务端根据商品和规格查出，再与请求选择的店铺比对；混合商家的请求直接拒绝，不偷偷拆单。
- 服务端重新校验：商品上架、商家状态、规格有效、数量、运费模板、地址属于当前顾客、价格。
- 幂等键绑定顾客、商家和请求摘要；同一个键但请求内容不同时，返回冲突。
- 每笔订单只占用一次库存，支付成功不再扣减；取消或超时释放只执行一次。订单创建、库存条件更新、订单项保存在同一事务内完成；最后一件被并发购买时只有一个成功。
- 超时关单要考虑支付回调竞态；晚到的成功支付进入可审计的异常处理。
- 区分取消未发货、退货验收入库、仅退款三种库存行为；库存恢复有独立的幂等记录。
- 发货数量不得超过未发货数量；退款前核对剩余可退金额，并发申请不得突破上限。

## 9. 支付、退款与结算（MS5）

- 本规格不指定收款产品，也不构成支付合规结论（Q4）。不默认采用"平台普通账户收全部货款再人工转给商家"。
- 订单级支付适配契约：

```text
createPayment(order, immutablePaymentAccount, idempotencyKey)
queryPayment(paymentAttempt)
closePayment(paymentAttempt)
createRefund(originalPaymentAttempt, refund, idempotencyKey)
queryRefund(refundAttempt)
verifyAndParseNotification(rawRequest)
```

- 每次支付明确订单、顾客、商家、渠道、收款账户标识及版本、币种、金额、请求标识、机构交易号。前端不能选择收款账户。
- 回调先验签，再按可信交易标识和原支付记录核对账户、金额、币种、订单。重复回调不得重复发货、扣库存、入账。
- 商家支付配置缺失时拒绝支付，不能回退平台默认账户。测试支付驱动只存在于测试环境；生产配置错误时拒绝启动对应能力。
- 退款沿原支付记录和原账户。销售、退款、通道费、平台费、商家应收分别记录。费用规则（Q5）确定之前，不开放自动结算和提现；不得把预测应收标成已到账。

## 10. 客服

- MS1 起商家令牌不得进入旧的全局客服后台、长连接鉴权、房间订阅（K01）。
- 商家专属客服如果在 MS4 之前没有实现，UI 和服务端都保持关闭；上线前必须通过 K02–K05。

## 11. 迁移、发布与回滚

### 11.1 迁移顺序

1. 记录分支、提交、工作树、运行版本；不得 `reset --hard`、`git clean`，不清理用户现有工作。
2. 在仓库外做可恢复的备份并验证；迁移先在隔离副本上演练。
3. 按真实结构增加实体和字段；不猜表前缀；不覆盖原始主键。
4. 建立历史归属映射；已确认自营的数据才映射到新建的自营商家；未知项单独列出并阻塞启用。
5. 回填附属对象，检查孤儿数据、跨商家关联、重复业务键、金额与行数差异。
6. 新入口确实强制写入归属之后，再加强非空、索引、唯一约束。
7. 验证顾客、订单、退款、上传文件和进行中的业务仍能查询和处理。

### 11.2 回滚限制

一旦产生多家商家的业务数据，**不得**让旧的单商家代码连接同一个数据库。回滚目标必须是兼容多商家结构和授权边界的版本。数据恢复是独立操作，需要明确批准，并说明数据损失窗口。不得为了让测试通过而清空数据库、删除订单、修改历史支付结果或关闭鉴权。

### 11.3 认证切换的发布准备（MS0b）

- 代码合入与真实发布分开。外部调用方没有盘点完，不阻塞隔离环境中的开发，但阻塞真实发布。
- 集成清单字段：脱敏账号标识、用途、负责人、最近使用证据及观察窗口、认证模式（JWT 或 MCP 直连凭据）、调用入口、能否重新取令牌、切换负责人、验证方式。没有使用日志不等于没有在用。
- 通知、切换、外部验收都需要另行授权。回退版本也必须保留已修复的认证边界。

### 11.4 配置开关

| 配置键 | 默认值 | 含义 |
|---|---|---|
| `marketplace.enabled` | `false` | 顾客端是否展示入驻商家的商品与店铺。存在未知归属的隔离数据时不得打开（MS2） |
| `marketplace.self_operated_mer_id` | 无（必填） | 自营商家的正整数 ID，由 MS2 迁移创建或查找后写入部署配置 |
| `marketplace.trade.disabled_features` | `['coupon','integral','balance','brokerage','activity']` | 新交易入口在服务端拒绝的功能（MS4） |
| `AUTH_SESSION_EPOCH`、`AUTH_STAMP_KEY`、`AUTH_ISSUER` | 无（前两项必填） | 会话 v2 配置（MS0b） |

## 12. 里程碑

| 里程碑 | 交付 | 合入门槛 |
|---|---|---|
| BASE | master 上的重建基线 + 文档 | 02 文档中的不变量全部成立；Z01/Z03/Z05 PASS |
| MS0a | 最小安全修复 + 最小隔离测试环境 | 10 文档中阶段为 MS0a 的用例全部 PASS；正常路径回归通过 |
| MS0b | 会话 v2 | 阶段为 MS0b 的用例 PASS；发布清单单独审批 |
| MS1 | 商家身份、merchantapi、MerchantContext | M 系列、A07、K01、D20 PASS；不暴露尚未隔离的商品接口 |
| MS2 | 商品及附属资源隔离、mer_id 迁移 | D、G 系列阶段用例 PASS |
| MS3 | 商家后台、平台审核、顾客店铺展示 | F 系列 PASS，回归 MS0a–MS2 |
| MS4 | 单店交易、评价 | O 系列、D19 PASS；客服启用时 K02–K05 PASS |
| MS5 | 支付、退款、对账 | P 系列 PASS，真实渠道项有授权和实际证据 |
| MS6 | 发布、恢复、限流、防回滚 | R 系列和全量已启用功能回归 PASS |

每个里程碑都自带迁移演练（如有 DDL）、回归和证据，不把证据拖到最后补。
