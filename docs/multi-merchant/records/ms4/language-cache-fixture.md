# 语言缓存安装序列的组件反馈

本记录对应 R101 的独立合成组件。PHP 8.2 三项语法检查通过；同一固定命令在两个全新 ISO-FULL 环境中，实际取得修复前退出1、修复后退出0。

`ms4-aftersale-review-normal.php` 将原语言服务查询和 `getLang()` 调用提取为 `m4ar_language_warm()`。实际复现证明：空表上的真实 `getLang()` 会缓存两个空映射，导入数据后的另一个真实 App 仍命中它们；`sys_lang_source_map` 应为116796字节，实际仍为6字节的序列化空数组。数据库已完整提交并回读，两个 App 的缓存配置一致。

修复仅作用于串行隔离夹具的预热：确认已安装的两个数据库映射均非空后，仅当 `sys_lang_source_map` 或 `lang_type_data` 的真实缓存严格等于空数组时，通过现有 `CacheService::delete()` 删除对应单键，再由原 `getLang()` 生成值、TTL 和标签。缺失、匹配或其他非空缓存不删；不手写缓存值，不清空 Redis，不改生产语言逻辑。原正常链的40项 wire、TTL、数据库、Redis、文件断言及业务责任完整保留。这不构成生产并发缓存修复。

新增入口 `help/audit-regressions/isolated/ms4-language-cache-normal.php` 分为两个独立 PHP/App 阶段：

1. `before-install` 在空的原语言表上调用真实 `getLang()`，记录它实际产生的缓存元数据，然后自然退出。
2. `install-and-warm` 从原安装 SQL 解码并以真实 PDO 事务写入完整的1条语言类型、1条国家和2515条语言代码；完整回读后创建新的真实 App，调用同一语言叶，并比较真实数据库映射与原缓存 wire。

返回0表示组件通过，1仅表示完成所有前置检查后出现指定的 `sys_lang_source_map` wire mismatch，2表示初始化或其它失败。程序不手写空缓存、不 mock 服务，也不以中文返回文本相同判断通过。只有真实执行后才能记录红或绿。

外部 runner 使用全新 ISO-FULL 网络、七个专用卷、本地固定镜像和只读源码。数据库只有三张原语言表及身份用 `audit_sentinel`，没有业务账号、订单或支付数据。原失败业务 Run 完成普通收尾和独立 zero 后，Root 才可运行新组件；新组件自身另行普通收尾和独立六查询 zero。

实际复现使用外部 `currentbafb-language-cache-feedback-source-r3` 的固定命令；原组件和完整安装 SQL 保持不变。失败环境的六个容器、一个网络、七个卷已普通收尾，独立六查询核零通过，其他53个容器的完整受保护记录保持一致。仓库外保存完整执行回执，仓库内不包含运行数据或凭据。

修复后的第二个环境保留同一组件、完整 SQL、runner 和原检查条件，只有共享语言叶改变。真实 `sys_lang_source_map` 恢复为116796字节，内容哈希与数据库预期一致，其余四项语言缓存 wire 也通过原检查；无关的类型缓存及其有效期保持不变。第二个环境也完成普通收尾和独立六查询核零。两轮各135条原生操作、独立核零各12条，全部完整回执已读回核对。

该结果只证明语言缓存组件修复；原完整正常链、40项 wire/TTL 验收、UI、设备、真实金融、发布及原19组未完成责任仍待后续验证。
