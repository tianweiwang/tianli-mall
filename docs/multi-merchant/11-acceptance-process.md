# 验收流程：每个模块做完后怎么验收

本文件规定：执行方交付什么、验收人按什么步骤检查、怎样复跑、怎样判定、怎样签收和合入。用例本身见 [10-acceptance-matrix.md](10-acceptance-matrix.md)。

## 1. 角色

| 角色 | 由谁担任 | 职责 | 不能做 |
|---|---|---|---|
| 执行方 | Codex（或其他开发代理、开发者） | 按计划实现；运行测试；提交交付包；修复验收缺陷 | 修改 README 中的里程碑状态；修改规格；自己签收 |
| 验收人 | 用户，或用户书面指定的人 | 按本文件 §3 检查；做出判定；签收；授权合入与推送 | 代替执行方改代码后直接签收 |
| 独立复核方（建议） | 未参与实现的另一个代理或人员，例如在 Claude Code 中对该分支运行 `/code-review` 与 `/security-review` | 独立复跑测试、审阅代码，向验收人提交意见 | 做出最终判定 |

安全相关的里程碑（BASE、MS0a、MS0b、MS1、MS2、MS5）**必须**有独立复核方参与 §3 的 V4 复跑和 V7 代码审阅。

## 2. 交付包

执行方在停止点提交以下内容，缺任何一项，验收人直接退回（判定"不受理"）：

| 编号 | 内容 | 位置 |
|---|---|---|
| P1 | 分支名、起点 SHA、交付 SHA；是否已推送 | 回传消息（12 文档 §7.2） |
| P2 | 报告 `report.md` | `docs/multi-merchant/records/<里程碑>/` |
| P3 | 逐子场景结果 `results.jsonl` | 同上 |
| P4 | 变更文件清单及与计划 **Files** 的差异说明 | `report.md` |
| P5 | 实际运行过的命令与退出码（不是计划中的命令） | `report.md` |
| P6 | 原始证据目录的位置（仓库外）与清单 | `report.md` |
| P7 | 迁移记录（如有 DDL）：前后表结构摘要、行数、归属分布、孤儿与冲突计数 | `report.md` 或单独文件 |
| P8 | 未运行项清单：用例、子场景、原因、所缺条件 | `report.md` |
| P9 | 遗留风险与下一步停止点 | `report.md` |

## 3. 通用验收步骤

验收人按顺序执行 V1–V10。每一步的结论写进 `records/<里程碑>/acceptance.md`（模板见 §8）。

### V1 交付包完整性
对照 §2 逐项打勾。`results.jsonl` 每行都必须有 `case_id`、`subcase`、`layer`、`phase`、`commit_sha`、`status`；`commit_sha` 必须等于交付 SHA。

### V2 范围审查
```bash
git diff --name-only <起点 SHA> <交付 SHA>
```
- 每个路径都必须出现在计划的 **Files** 中，或在报告 P4 中有合理说明。
- 以下路径出现即退回，除非计划明确要求：`crmeb/vendor/`、`crmeb/public/`（MS6 按 Q2 决定后除外）、`crmeb/.env`、任何含凭据的文件、`help/docker/run.sh`。
- 规格类文档（00、01、03、10、11、12）被修改且没有用户批准记录 → 退回。

### V3 提交审查
```bash
git log --oneline <起点 SHA>..<交付 SHA>
```
- 提交顺序符合计划：测试提交在修复提交之前（MS0a 起每个任务如此）。
- 没有合并备份分支、没有改写已推送的历史。
- 每个提交只做计划中一个任务的事。

### V4 独立复跑
在干净的 worktree 和新建的隔离环境中重新运行，**不使用**执行方的运行目录：
```bash
git worktree add /tmp/accept-<里程碑> <交付 SHA>
cd /tmp/accept-<里程碑>
help/audit-regressions/isolated/bootstrap.sh
# 按 report.md 中 P5 列出的命令逐条运行，记录退出码
help/audit-regressions/isolated/teardown.sh <RUN_ID>
```
- 复跑结果与交付的 `results.jsonl` 逐子场景比对，状态不一致的每一项都要查明原因。
- 不稳定（同一子场景两次结果不同）的用例记为 FAIL，直到执行方修复。
- 对需要基线对照的里程碑（MS0a），在 `AUDIT_BASE_SHA` 上以 `AUDIT_PHASE=baseline` 抽样复跑至少 A12、A27、A19，确认基线结果与报告一致。

### V5 用例覆盖
- 10 文档中阶段属于本里程碑的每条用例、每个子场景，在 `results.jsonl` 中都有记录。
- 没有把 NOT RUN、BLOCKED 写成 PASS；`finding_kind` 填写合理（不能把"既有拒绝回归"写成"本轮修复"）。
- 此前所有里程碑的自动化用例都被回归运行。

### V6 副作用证据抽查
从负向用例中至少抽查 5 个子场景（§5 中列为"必查"的必须包含在内），打开原始证据：
- 前后快照的表与键覆盖了该用例可能写入的位置；
- `db_diff`、`cache_diff` 为空，或只包含 03 文档 §4.3 允许的变化；
- 响应体中没有泄露受保护的数据。

### V7 代码审阅
按 §5 中该里程碑的"审阅重点"逐条检查；建议由独立复核方运行 `/code-review` 和 `/security-review`，验收人对每条意见给出"接受 / 不接受（理由）"。

### V8 正向回归与手工走查
- 自动化正向用例全部通过。
- 涉及界面的里程碑（MS3 起），验收人按 §5 的走查脚本亲自操作一遍，截图存档。

### V9 迁移验收（有 DDL 时）
- 迁移在隔离环境演练过两次（G01），结果一致。
- `check` 能识别已完成与冲突状态。
- 前后行数、主键、文件路径、金额汇总一致；归属分布与用户确认的映射一致。
- 真实库执行是单独的 L4 操作，**不在本次验收范围内**；验收通过不代表允许执行。

### V10 判定与签收
按 §4 判定，填写 `acceptance.md`，并在 README §2 更新状态。

## 4. 判定规则

| 判定 | 条件 | 后续 |
|---|---|---|
| **通过** | V1–V9 全部满足；本里程碑"必须 PASS"的用例全部 PASS；"允许延后"的项都有明确原因和补测里程碑 | 验收人更新 README 状态为"已验收"，授权合入（§6） |
| **不通过** | 任一"必须 PASS"的用例 FAIL；复跑结果不一致；范围越界；出现 §4.1 的阻塞情形 | 在 `acceptance.md` 中列出缺陷编号；执行方在同一分支追加提交修复；重新提交交付包；**全量**重新验收 |
| **阻塞** | 缺少环境、授权或外部条件，导致"必须 PASS"的用例无法运行 | 记录所缺条件与负责人；状态保持"待验收" |
| **不受理** | 交付包不完整（V1） | 退回补齐 |

不设"有条件通过"。需要延后的项只能是 §5 中明确列为"允许延后"的项。

### 4.1 一票否决

以下任一情况出现，判定为不通过，并在修复前停止后续里程碑：

- 跨应用身份混用、失效账号仍有权限；
- 跨商家私有数据泄露或写入；
- 未知归属的数据被迁移、自营默认回退（`mer_id = 0` 被当作自营或全局）；
- 错收款、超额退款；
- 业务数据丢失；
- 测试写入了生产或业务实例；
- 为了让用例通过而放宽断言、删除用例、修改期望值或关闭鉴权。

## 5. 各里程碑的验收清单

### 5.1 BASE

- **必须 PASS**：Z01、Z03、Z05；02 文档 Task 5 的不变量（变更集合一致、演示凭据未回流、备份检出未改动）；`security.php` 23/23。
- **允许延后**：无。
- **必查证据**：`base-diff.txt` 与输入清单的逐项对照；`backup-status-before.txt` 与 `backup-status-after.txt`。
- **审阅重点**：清单 B 中 24 个文件的内容与备份检出（去掉 CR 后）一致；新基线没有 CRLF；`crmeb/.env` 已停止跟踪。
- **签收后**：记录 `AUDIT_BASE_SHA`；授权推送 `codex/audit-base`（L3），并决定是否向 master 发起 PR。

### 5.2 MS0a

- **必须 PASS**：10 文档中阶段为 MS0a 的全部用例（A10、A17、A18、A21、A23 只看 MS0a 部分）；`security.php` 原有 23 个及新增用例；`selftest.php`。
- **允许延后**：Z08 中"实际在用的调用方"一栏可以是"未知"（发布前在 MS0b 补齐）。
- **必查证据**：A12（两个子场景）、A27（`eb_cache` 与 `eb_store_product` 的前后快照）、A19（关闭后访问与刷新）、A09（16 组矩阵）、A26。
- **审阅重点**：
  - 四个应用的 `parseToken` 中，验签发生在使用任何载荷字段之前；
  - type 由接收端写死，没有从令牌中读取后再分支；
  - 失败路径中没有业务写入，`authFailAfter` 已删除；
  - 只有在"记录属于本应用且账号失效"时才删除白名单记录；
  - `verifyAuth()` 中不再有未登记放行和 `crud/` 放行；白名单内容与 SP-MS0a-1 确认的一致；
  - `SystemMenus` 的写操作都清理了权限缓存；
  - 没有改动令牌格式、没有新增表或列。
- **签收后**：记录 `SECURITY_BASE_SHA`。部署到任何真实环境需要另行 L4 授权，并提前告知管理员与对外调用方：已关闭的对外账号的现存令牌将失效。

### 5.3 MS0b

- **必须 PASS**：阶段为 MS0b 的全部用例与 A10、A17、A18、A21、A23 的 MS0b 部分；全部 MS0a 用例回归；ISO-FULL 自检。
- **允许延后**：Q6、Q7 若决定不纳入，对应任务不做。
- **必查证据**：A25（并发与故障注入）、A29（快照恢复与 epoch 轮换）、A24（旧令牌在旧键仍存在时被拒绝）、A21 的部分失败场景。
- **审阅重点**：Lua 脚本先校验后写入；访问与刷新路径没有任何"键不存在就创建"的代码；没有 `FLUSHALL`、`KEYS`；凭据变更入口全部接入 `AccountChangeGuard`（对照报告中 grep 出的入口清单）；cutover 文档中没有"已通知""已部署"等未发生的事实。
- **签收后**：真实切换需要 L4，并以集成清单核实完毕、通知已由用户发出为前提。

### 5.4 MS1

- **必须 PASS**：M01–M10、A07、K01、D20；全部 MS0a、MS0b 用例回归；迁移 G01 针对 MS1 结构。
- **允许延后**：M09 在 worker 只能串行时，记录能力边界即可。
- **必查证据**：M05（同一 PID 的三个任务）、M03、M07（8 组）、K01 的 WebSocket 子场景。
- **审阅重点**：`MerchantContext` 没有存放在静态属性、全局变量或容器单例中；服务方法显式接收上下文；merchantapi 没有商品路由；新菜单与权限标记以 `marketplace` 开头；审计日志不含密码、令牌、设置链接；一次性设置链接只存哈希。
- **手工走查**：用平台账号建立商家并审核 → 复制设置链接 → 在无痕窗口设置密码并登录商家 API（可用 curl）→ 平台封禁该商家 → 商家下一次请求 401。

### 5.5 MS2

- **必须 PASS**：阶段为 MS2 的 D、G 用例；全部此前用例回归。
- **允许延后**：G04、G05、G06 中依赖真实数据副本的子场景，在未获 L3d 授权时可为 BLOCKED，但 `marketplace.enabled` 在这些子场景通过前不得打开。
- **必查证据**：D04、D05（批量混入他店 ID 后 A 自己的商品也未改变）、D11（逐键比对公众字段）、D15、G02 的隔离清单。
- **审阅重点**：商家侧代码没有直接调用 BaseDao 直查方法访问受保护表；批量写入的 `WHERE` 同时含 `id IN` 与 `mer_id`，且核对受影响行数；没有回退到运费模板 `id = 1`；公众接口使用字段白名单；`searchMerIdAttr()` 不再回退 0；审核字段不能由商家写入。
- **手工走查**：用 A、B 两个商家的 API 各建一个商品并送审 → 平台审核通过 A、驳回 B → 顾客端只看到 A 的商品且显示 A 的店铺。

### 5.6 MS3

- **必须 PASS**：F01–F04；此前全部用例回归。
- **允许延后**：真机与小程序生产包（受正式域名限制），需写明原因。
- **必查证据**：F03 的截图与数据库结果对应；F04 中"保存失败"的截图与数据库未变化。
- **审阅重点**：商家前端没有平台菜单、系统工具；token 存储键独立；401/403/404 的处理；锁文件已提交且 `npm ci` 可复现。
- **手工走查**：按 08 文档 Task 2、Task 3、Task 4、Task 5 的测试步骤，在浏览器中亲自操作一遍。

### 5.7 MS4

- **必须 PASS**：O01–O12、D19、R05 的下单子场景；若开放商家客服，K02–K05；否则 K01 回归。
- **允许延后**：无。
- **必查证据**：O04（并发最后一件）、O02、O03、O11。
- **审阅重点**：库存条件更新的影响行数检查；所有交易写入在同一事务中；幂等键冲突返回 409；存量权益的处理与 SP-MS4-1 的确认一致。
- **手工走查**：同一顾客把 A、B 商品加入购物车，分别结算；A 商家发货；B 商家尝试查看 A 的订单被拒绝。

### 5.8 MS5

- **必须 PASS**：P01–P11 中不需要真实渠道的子场景。
- **允许延后**：需要真实渠道的子场景（EXTERNAL），在没有 L4 授权时为 BLOCKED；此时只能判定"阻塞"，不能上线收款。
- **必查证据**：P03、P04、P08、P11。
- **审阅重点**：收款账户由服务端按订单解析；回调先验签后定位；所有状态推进是条件更新；测试驱动在生产配置下无法注册；没有任何代码路径回退到平台默认账户。

### 5.9 MS6

- **必须 PASS**：R01–R06；全量回归（ISO-FULL 与预发布环境各一次）。
- **允许延后**：无。
- **审阅重点**：发布脚本的版本门槛；备份不含认证会话；日志扫描结果；Q2、Q3 的决定已落实。
- **签收后**：真实发布另需 L4，按发布清单逐项由用户确认。

## 6. 合入与分支规则

| 里程碑 | 交付分支 | 合入目标 | 合入方式 |
|---|---|---|---|
| BASE | `codex/audit-base` | 推送后由用户决定是否向 `master` 发起 PR | 普通合并，不压缩（保留迁移、审计、文档的分步提交） |
| MS0a | `codex/ms0a` | `codex/audit-base`，随后同 BASE 一起或单独向 `master` 发起 PR | 同上 |
| MS0b | `codex/ms0b` | 同 MS0a | 同上 |
| MS1–MS6 | 在 `feature/multi-merchant-v0.1` 上按里程碑提交 | 每个里程碑验收后打标签 `mm-v0.1-ms<N>-accepted`；MS6 验收后由用户决定是否合入 `master` | 普通合并 |

- 推送、开 PR、合并都需要验收人授权（L3）。
- 验收后发现的缺陷：新开修复提交，重新走受影响里程碑的 V4–V10。

## 7. 回归节奏

每个里程碑交付前，执行方运行此前所有里程碑的自动化用例；验收人在 V4 中复跑。任何旧用例从 PASS 变为 FAIL，都按"不通过"处理。
