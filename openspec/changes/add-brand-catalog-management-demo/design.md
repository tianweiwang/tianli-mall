## Context

当前 `services` 没有状态与门店范围，`products` 只有展示用的 `selling` 状态，消费者分类、首页、详情和门店目录直接读取全量数组。品牌页虽然命名为“目录管理”，但只提供查看抽屉。

详细交互与边界见 `docs/superpowers/specs/2026-08-03-brand-catalog-management-design.md`。

## Goals / Non-Goals

**Goals:**

- 用一个本地状态模型串联品牌维护、门店只读和消费者可见性。
- 通过独立领域函数校验目录变更，避免页面直接修改对象。
- 保持历史交易快照稳定，并在新交易边界重新校验商品。

**Non-Goals:**

- 不实现删除、上传、排班、门店自主定价、独立库存或远程接口。
- 不把本地 Demo 描述成生产后台。

## Decisions

### Decision: 统一使用 `active` / `inactive`

服务和商品共用状态词，初始目录全部为 `active`。这让共享选择器和状态按钮可以复用，避免商品 `selling`、服务无状态的双口径。

### Decision: 用 `storeIds` 表示目录投放范围

每个目录项保存适用门店 ID 数组。品牌方可选择营业门店，门店端和消费者端只读取 `active` 且包含当前门店的项目。停用门店不作为新选择项。

### Decision: 领域变更与查询分离

`catalogTransitions.js` 负责输入规范化、校验、ID、创建、更新和上下架；`selectors.js` 负责按门店查询。页面只通过 `demoStore.commit()` 调用领域函数。

### Decision: 历史数据不追随目录变化

目录下架或编辑不删除预约时段、不改订单条目、不改预约和结算记录。加购和下单重新检查当前目录状态、门店范围与库存。

### Decision: 新服务不自动创建时段

服务新增后可在适用门店目录出现；没有 `slotInventory` 时显示到店咨询。排班属于另一个业务能力，不在本变更中隐式生成。

## Risks / Trade-offs

- 版本升级会重置已有浏览器本地演示动作；这是避免旧状态字段缺失的确定性选择，重置后仍保留固定示例数据。
- 商品库存是品牌维护字段，但本变更不模拟订单扣减；页面不宣称这是实时仓储库存。
- 图片只接受路径或 URL 并提供内置默认图，不模拟文件上传成功。

## Migration Plan

1. 扩展种子构造器并增加服务、商品序列。
2. 将 `DEMO_VERSION` 升级，旧状态自动回到新种子。
3. 不迁移历史 `selling` 对象，避免半新半旧状态。

## Rollback

回退代码并恢复上一静态发布目录。浏览器若已写入新版状态，旧版本会因版本不匹配恢复旧种子，不需要数据脚本。
