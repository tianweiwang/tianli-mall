## Context

已确认设计位于 `docs/superpowers/specs/2026-07-30-franchise-platform-h5-demo-design.md`。Demo 的目标是让甲方沿一条连续链路看懂门店归属、下单、预约、核销、门店收益和品牌分账，而不是模拟一套真实后端。

现有 CRMEB 管理后台启动入口会加载接口和远程脚本，正式商城也依赖运行中的 API，因此不能直接作为 Demo 外壳。新工程只复用视觉语言和筛选后的本地素材。

## Goals / Non-Goals

**Goals:**

- 用同一套静态产物展示消费者、门店和品牌方三种角色。
- 在同一浏览器内保证订单、预约、业绩和分账状态一致。
- 让门店入口码和核销码能够被真实二维码解码器识别。
- 支持静态 Nginx 子目录部署，并在移动端和桌面端达到演示质量。

**Non-Goals:**

- 真实登录、接口、数据库、支付、退款、分账、微信授权或生产核销。
- 跨设备实时同步。
- 门店自建商品、独立库存、拆单、自主发货或其他完整多商户能力。

## Decisions

### 独立 Vue 2 静态工程

使用 Vue 2.7、Vue Router 3、Element UI 2 和 Vite。路由使用 hash 模式，构建基础路径使用相对路径。工程不导入正式后台的启动文件、接口层或状态仓库，避免产生隐式网络请求。

### 单一版本化本地状态

所有页面通过 `src/mock/store.js` 访问一个版本化 JSON 文档。`src/mock/transitions.js` 是订单、预约、核销和分账状态变更的唯一入口。状态损坏或版本不匹配时恢复确定性的种子数据并记录恢复提示。

### 二维码载荷与扫描

门店入口码编码当前部署地址的 hash 路由。业务核销码编码带版本、业务类型、业务编号、门店编号、签发时间和校验值的 Demo URL。校验值只检测载荷损坏，不宣称生产防伪。扫描优先匹配本机记录；跨设备时只在扫描设备导入模拟记录。

### 页面边界

消费者端使用全屏移动 H5 和固定四项底部导航。门店端和品牌方使用同一后台壳层，但菜单和数据范围不同。门店只见本店数据且商品只读；品牌方可跨店查看并推进模拟分账状态。

## Risks / Trade-offs

- `localStorage` 不能跨设备同步。界面必须明确跨设备扫描仅影响扫描设备。
- 摄像头通常要求 HTTPS。部署说明和扫描页必须同时提供图片识别与备用编号。
- 浏览器存储可被手工修改。Demo 校验值只做损坏检测，不能被描述为安全签名。
- 页面数量较多。先实现共享状态和壳层，再按主流程扩展页面，避免出现大量互不联动的静态页面。

## Verification

- 单元测试覆盖状态初始化、门店归属、金额恒等式、容量释放及四类核销结果。
- 浏览器测试覆盖完整主演示链路和数据重置。
- 生成二维码后用独立解码器回读载荷。
- 在 375x812、390x844、430x932、1280x800 和 1440x900 视口检查截图、溢出和控制台异常。
- 构建后通过静态服务器运行，断开 CRMEB API 仍能完成全部流程。
